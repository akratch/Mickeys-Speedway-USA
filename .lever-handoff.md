# Lever-diagnosis field test (decomp-workbench 0.8.0), lane `lever-res2`

First campaign use of `diagnose`'s `lever:` block on resident sweep-flat
plateaus. Ten targets were assigned; six could not be opened (below). Four
were diagnosed, seven builds were spent, one function improved, none matched.

## Reopen gate

`tools/lane_status.py` reads `config/lane-reopen-authorizations.us.json` from
its resolved *base* (`campaign/unchain`), never from the working branch, so a
pin committed in a lane is invisible to the default invocation. Every status
below was therefore confirmed with `--base HEAD` after committing the pin.

Six targets were skipped because no pin can reach them:

| Symbol | `lane_status` state | Why unpinnable |
|---|---|---|
| `func_8006E7E0` | stale-ledger / prose-needs-remeasurement | `source_commit` is null: the shard exists but no plateau commit names the target, and `assignment_status` returns before the authorization is consulted |
| `func_8005807C` | same | same |
| `func_80004454` | same | same |
| `func_8000471C` | same | same |
| `func_80002188` | same | same |
| `func_80045BBC` | already-integrated/exhausted | its ledger evidence is the legacy triage file, not a shard; a pin naming that `ledger_commit` fails validation (`ledger_commit does not identify the authorized source path`) and a null `ledger_commit` does not match the computed one |

`func_80045BBC` is a genuine gap in the pin schema: a symbol whose only
evidence is legacy-ledger prose has no expressible authorization.

## Per function

### `func_800056A4` (src/main/objects.c) -- 8 words, unchanged

- **lever block (no trace):** `lever: temp-ring`, no `edit (...)` line, one
  `capture:` for `DKWB_UGEN_TRACE`. Correct behaviour per the documented rule.
- **trace captured:** `DKWB_UGEN_TRACE=1` through
  `ido-instrumented/cc`, whole-TU log, `--lever-proc 11`.
- **lever block (with trace):** `edit (read-the-field-directly)`, evidence
  `source line(s) 1614, 1617 consume more than one pop each`.
- **edits tried (3 builds):** inline the `s32 **table` local at its use;
  respell the outer scale as pointer arithmetic; both together.
- **result:** every variant compiled **byte-identically** (`sha1=9cf9478f1144`
  on all three). The site is saturated in the sense of L25.
- **field-test note:** the named edit was *inert here*. L76's construct is a
  **struct field** read through a local; this local carries a cast integer
  constant, and cfe canonicalises it away. The lever block named the edit from
  the pop count alone without checking that the line's local is of the shape
  the law measures. The `--ring-trace` line attribution itself was accurate
  and useful; the edit selected from it was not.

### `func_80005868` (src/main/objects.c) -- 8 words -> **6 words**

- **lever block (no trace):** `lever: stack-home`, named
  `edit (reuse-an-existing-local-as-carrier)`, with
  `or (drop-a-declared-local)` and `or (declare-the-pair-later)`.
- **trace captured:** none. The block's own evidence (frames equal, one
  displaced home) plus the **pool lane**, which showed the candidate carrying
  one extra web at slot 0, was sufficient; the `capture:` line asked for a
  `CDX_SYMTAB` ladder that would only have corroborated the declared count.
- **edits tried (7 builds):** drop the `index` local (direct nested read);
  add a pointer local; move that pointer above the buffer; move `index` above
  the buffer; finally `index` **and** an `entry` pointer both declared before
  `u8 buffer[0xC0]`.
- **result:** the last form is **strictly better**: 8 -> 6 words, frame
  unchanged at `-0xE0`, instruction count unchanged at 22, and both
  stack-displacement constants closed (`addiu a1,sp,24`, `lh v0,52(sp)`).
  Retained and re-finalised.
- **what remains:** a five-site `v1`/`v0` web. The target reads the table
  index into a **ring temp**; the candidate colours it. Dropping the local
  does reproduce the target's pool lane exactly, but costs an `a0`
  spill/reload pair and 8 bytes of frame (23 words). No form produced both.
- **field-test note:** the `or (...)` directions were the load-bearing part.
  The headline `edit (...)` -- reuse a dead local as carrier -- was not
  applicable (no dead local exists in a six-line function), while
  `drop-a-declared-local` was the direction the pool lane pointed at. The
  block ranks by frame arithmetic alone and does not read the pool lane it
  prints two paragraphs above, which is where the answer was.

### `func_8003A2C8` (src/main/menu.c) -- 8 words, unchanged

- **lever block:** `lever: none-known`, `routing=permuter-first`,
  `reachability=permuter-target`, plus the note that 1 of 5 substitutions
  wants `t6`, a register the era's colouring pass never hands out.
- **trace captured:** none; no edit family is named and the permuter is out of
  scope for this lane.
- **result:** recorded, no build spent. Honest and useful: the block declined
  to guess, and the ring-only-target-register note is a real reason no colour
  lever can close it.

### `debug_text_width` (src/main/diprint.c) -- 7 words, unchanged

- **lever block:** `lever: none-known` with **three** `capture:` lines
  (ring, emit, as1) and two `see also` proofs, one of which
  (`uopt-coalescing-tie-break`) states that hand-merging the two locals the
  pool lane suggests produced a byte-identical object.
- **trace captured:** none. The `see also` proof predicted the outcome of the
  only edit the evidence supports, so per lever 43 it was read rather than
  re-derived -- one build was spent to confirm the prediction.
- **edit tried (1 build):** introduce a separate classification carrier
  (`s32 code`) declared last, and route the `0x21..0x80` range test and the
  three `- 0x21 / - 0x40 / - 0x60` subtractions through it.
- **result:** **byte-identical** (`sha1=4fbf69462dda`). uopt coalesced the
  carrier into `pad`, exactly as the `see also` proof says. Confirms L72 as a
  side effect: the extra declared local was free (frame stayed `0x138`).
- **residual:** the target keeps the character in `v1` and a copy in `v0`
  (`beq`/`move` where the candidate emits `beql` with the loop's next `lbu` in
  the delay slot). Splitting the web requires the two values to differ
  somewhere, and they do not.
- **field-test note:** `none-known` with three captures is the weakest output
  of the new block. It offered no ranking, and the actionable content was in
  the `see also` catalogue entry, not in the lever. A `lever: unreachable`
  verdict citing `uopt-coalescing-tie-break` would have been the correct call
  and would have saved the build.

## Summary of the field test

| Function | lever class | edit named | trace asked | trace used | outcome |
|---|---|---|---|---|---|
| `func_800056A4` | temp-ring | yes, after the trace | ring | yes | inert (byte-identical x3) |
| `func_80005868` | stack-home | yes (wrong one of three) | ladder | no, not needed | 8 -> 6 words |
| `func_8003A2C8` | none-known | no | three | no | correctly declined |
| `debug_text_width` | none-known | no | three | no | see-also proof was right |

Two systematic findings:

1. **The block names an edit family without checking the shape the law was
   measured on.** `read-the-field-directly` cites L76, which is about a
   *struct field*; the block applied it to a line whose local is a cast
   integer constant, and all three spellings were byte-identical.
2. **`stack-home` ranks its three directions from frame arithmetic and
   ignores the pool lane it just printed.** On `func_80005868` the pool lane
   named the surplus web outright; the frame-only ranking put that direction
   third.

One thing the block got exactly right: on both `none-known` functions it
refused to guess, and on `func_8003A2C8` the ring-only-target-register note is
a measurement no hand lever can argue with.
