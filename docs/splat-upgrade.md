# Splat 0.35.2 -> 0.50.0 evaluation

Evaluated on `lane/splat-upgrade`, worktree
`mickey-lane-splat-upgrade`, against a separate venv (`.venv-splat50`,
Python 3.11) so the shared `.venv` used by other running lanes was never
touched.

## Result: extraction, then build, are byte-identical

- `gmake PYTHON=.venv-splat50/bin/python extract` (splat64 0.50.0,
  spimdisasm 1.42.4, rabbitizer 1.16.2) succeeded against the tree's
  existing `mickey.us.yaml` and `tools/overlay_atlas.py` output with
  **zero config changes**. No renamed options, no new required keys, no
  vram-overlap failures.
- `gmake PYTHON=.venv-splat50/bin/python -j12 verify` produced
  `build/mickey.us.z64` matching the expected hash
  `507341c0a40ca3e9a7cee969b396ee53facfb548`. The ROM is still
  byte-identical.
- Diffing the freshly extracted `asm/` (315 files) against a copy taken
  before the re-extract (`diff -rq`, `build/asm-0.35` vs `asm/`) found
  **all 315 files present in both trees, no additions, no removals**.
  275 of the 315 differed; every one of those differences is a single
  line: the `/* Generated by spimdisasm 1.36.1 */` -> `1.42.4` banner
  comment. Function boundaries, subsegment splits, and symbol names are
  unchanged file-for-file.

Conclusion: for this repo's config, 0.50 is a drop-in replacement for
0.35.2. No yaml or `tools/overlay_atlas.py` changes were required or
made beyond bumping the pin.

## Why the config didn't need to change

`docs/acceleration-survey.md` §10 and the splat CHANGELOG (0.36 -> 0.50)
flag three headline changes in this range, all specific to overlay
symbol resolution:

1. **Autogenerated overlay symbol naming** now embeds both vram and rom
   (`D_{VRAM}_{ROM}`) instead of vram alone, fixing collisions between
   overlays that share vram. `tools/overlay_atlas.py` already sets
   `symbol_name_format: $SEG_$VRAM_$ROM` explicitly on every generated
   overlay segment (see the `render_yaml_block` function), so this repo
   was already on the post-0.50 naming scheme before the upgrade — the
   fix changes splat's *default*, which this yaml overrides.
2. **`prioritized_segments`**, a new yaml attribute for resolving symbol
   references across overlays that share an `exclusive_ram_id` (this
   repo's 107 overlays all share `exclusive_ram_id: overlay_modules`).
   Extraction never needed it: every overlay's data/rodata/relocation
   tail is emitted as an opaque `bin` subsegment, not disassembled with
   cross-overlay symbol references, so the ambiguity `prioritized_segments`
   exists to resolve is never exercised by this project's overlay model.
3. **Stricter vram-overlap checks**. The atlas's synthetic-VMA design
   (every overlay's `type: code` segment shares `vram: 0xF0000000`) is
   exactly the shape that would trigger a naive overlap check, but the
   shared `exclusive_ram_id` is the mechanism splat uses to permit it,
   and that mechanism is unchanged between 0.35 and 0.50 — the stricter
   check tightened *unflagged* overlaps, not this deliberately-declared
   one.

No other breaking option renames in the 0.36-0.50 changelog apply to
this yaml (no image/gfx segments, no custom `_gp` expression, no
`alabel` usage).

## Question 4: does 0.50 remove the need for the overlay relocation
## fixup tools?

**No.** `overlay_undefined_syms.us.txt` and the
`filter_elf_relocations.py` / `rebind_elf_relocations.py` post-process
steps address a problem entirely downstream of splat, in the IDO 5.3
compiler's codegen when *compiling adopted C back into an object file*
— not in splat's disassembly or symbol lookup during extraction. Splat
only ever produces `asm/` and the linker script from the ROM; these two
tools run against `build/src/overlays/.../*.c.o`, the objects IDO
produces per translation unit at build time.

Worked example — `src/overlays/o007/overlay7EntryPool.c`
(`Makefile:732-750`, unchanged across the extraction diff):

```
$(BUILD_DIR)/$(SRC_DIR)/overlays/o007/overlay7EntryPool.c.o: POSTPROCESS = \
    ... normalize_elf_instructions.py ... && \
    rebind_elf_relocations.py $@ .text \
        0x1ac:gOverlay7ActiveTail:gOverlay7FreeHead \
        0x1b0:gOverlay7ActiveTail:gOverlay7FreeHead \
        0x1b8:gOverlay7FreeHead:gOverlay7ActiveTail \
        0x1bc:gOverlay7FreeHead:gOverlay7ActiveTail && \
    filter_elf_relocations.py $@ .text \
        0x0ac:5:gOverlay7ActiveHead 0x0b0:6:gOverlay7ActiveHead \
        ...
```

`rebind_elf_relocations.py`'s own header states the problem directly:
"the compiler reuses one undefined symbol for multiple address
materializations but retail's link result requires different bindings
at specific sites." IDO compiled `overlay7EntryPool.c` and picked one
of two aliased addend symbols (`gOverlay7ActiveTail` /
`gOverlay7FreeHead`) at four specific instruction offsets; the tool
swaps the symbol index on exactly those four relocation records so the
linked object matches what retail's own compile produced. `overlay_
undefined_syms.us.txt` is the parallel mechanism for whole-symbol
addend aliases (`gOverlay14Reset1C = 0x1C;` etc.) rather than per-offset
swaps — both exist because IDO's registerization/addend-materialization
choices for these overlay-relative constants don't always match retail
byte-for-byte, and the fixups are asserted (fail loudly) rather than
silently applied, so they double as a correctness check on every build.

Splat's job stops at producing `asm/`, `mickey.us.ld`, and the
`overlay_undefined_syms.$(VERSION).txt`/`undefined_*` linker inputs from
the ROM; it has no visibility into what IDO does when *recompiling*
adopted C, so no version of splat's overlay symbol lookup — 0.50's
vram+rom naming included — touches this class of problem. Confirmed
empirically too: the asm/ diff above is banner-only, meaning splat 0.50
extracted the exact same subsegment boundaries and symbol names 0.35.2
did, so none of the `POSTPROCESS` relocation-fixup lines change either.

## Changes made in this lane

- `requirements.txt`: `splat64[mips]` 0.35.2 -> 0.50.0, `spimdisasm`
  1.36.1 -> 1.42.4 (the versions the `[mips]` extra resolves to; it also
  pulls in `n64img`, `crunch64`, `pygfxd`, `rabbitizer`, which splat's
  own `import splat` chain requires eagerly even though this project
  uses no image/gfx segments).
- `mickey.us.yaml`, `tools/overlay_atlas.py`: **no changes**. Extraction
  and the build were already correct against 0.50 as written.
- **The shared `.venv`** (symlinked into every lane, used by other
  running lanes) was **not** touched or upgraded. This evaluation used
  a separate `.venv-splat50` inside this lane only. Landing the
  `requirements.txt` bump for real means re-running `gmake setup` (or
  `pip install -r requirements.txt`) in the shared venv once no other
  lane is mid-build against it.

## Go/no-go

**Go**, with one sequencing caveat. The upgrade is a net win — newer
spimdisasm/rabbitizer, and 0.50's stricter overlap checking and
`prioritized_segments` are useful safety nets should the overlay model
ever grow a case that needs them — and it costs nothing here: same
`asm/` tree, same ROM hash, no yaml rewrite. The only blocker is
operational, not technical: the shared venv is used by other lanes
mid-flight, so upgrading it should happen when no other lane is
actively running a build, followed by one `gmake distclean && gmake
setup && gmake verify` in the main repo to confirm the same
byte-identical result there before merging past this lane.
